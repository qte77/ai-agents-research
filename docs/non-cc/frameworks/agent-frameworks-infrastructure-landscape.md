## 1. Multi-Agent Orchestration Frameworks

- [LangGraph](https://github.com/langchain-ai/langgraph) — graph-based stateful orchestration with checkpointing and conditional routing (MIT); the base for many harnesses below.
- [CrewAI](https://github.com/crewAIInc/crewAI) — role-based crews with sequential/hierarchical/consensus execution (MIT).
- [AutoGen / AG2](https://github.com/ag2ai/ag2) — conversational multi-agent framework with group chat and code execution (Apache-2.0).
- [PydanticAI](https://github.com/pydantic/pydantic-ai) — type-safe agents on Pydantic v2 with durable execution + MCP/A2A; the framework this repo's evaluation work builds on. Its [capabilities system][pai-caps] (Jun 2026) bundles instructions + tools + model settings into composable units that support **on-demand / deferred loading** (`defer_loading=True`) — a capability's context is injected only when the agent requests it, trimming per-run tokens (PydanticAI's progressive-disclosure / "skills" answer); capability-scoped hooks fire only on load. Companion managed services: the Pydantic AI Gateway (routing) and [Logfire](../protocols/agent-observability-methods-analysis.md) observability. A community **full-stack starter** ([Vstorm template](https://pydantic.dev/articles/full-stack-ai-agent-template-pydantic-ai), Jun 2026) scaffolds a production PydanticAI app — Next.js 15 + FastAPI + Postgres/Mongo + Redis, WebSocket streaming, JWT auth, Alembic migrations, Logfire/OpenTelemetry tracing, Docker deploy (LangChain swappable for PydanticAI). A separate capability library, [`pydantic-ai-harness`](https://github.com/pydantic/pydantic-ai-harness) ("batteries for your agent", MIT, 595★; iterates faster than core), ships ready agent capabilities — a sandboxed **CodeMode** (Python via the Monty sandbox), filesystem + shell tools (path-traversal guards / allowlists / timeouts), and provider-adaptive web search — on a *fall-up* model (a local implementation works with any model, auto-switching to provider-native when available); 30+ capabilities are on the roadmap. It is the product face of Pydantic's "harness > model" thesis (see [agentic-engineering-disciplines-landscape.md](../../sdlc-lcm/agentic-engineering-disciplines-landscape.md)).
- [LlamaIndex Agents](https://github.com/run-llama/llama_index) — RAG-optimized agents over 100+ data sources.
- [Letta](https://github.com/letta-ai/letta) — stateful agents with hierarchical self-editing memory, by the [MemGPT](https://arxiv.org/abs/2310.08560) authors (Apache-2.0).
- [Agno](https://github.com/agno-agi/agno) — high-performance multi-agent runtime with built-in memory/session, FastAPI app, strong MCP support; pitches itself as a "self-driving agent platform" built on the **AgentOS** runtime ([agno.com](https://agno.com)) — one database for sessions/memory/knowledge/traces and one control plane, deployable via REST, MCP (ChatGPT/Claude), Slack, Discord (Apache-2.0; 42.3k★, `gh api` 2026-09-24).
- [Microsoft Agent Framework](https://github.com/microsoft/semantic-kernel) — unifies Semantic Kernel + AutoGen (public preview Oct 2025); dual agent/workflow orchestration, A2A + MCP, .NET + Python.
- [OpenAI Agents SDK](https://github.com/openai/openai-agents-python) — lightweight provider-agnostic agents with handoffs, guardrails, tracing (Mar 2025).
- [Google ADK](https://github.com/google/adk-python) — LLM/Workflow/Custom agents with built-in eval + MCP; deploys to Vertex AI Agent Engine (Apr 2025).
- [AWS Agent Squad](https://github.com/awslabs/agent-squad) — intent-classification query routing across agents, Python + TypeScript.
- [Swarms](https://github.com/kyegomez/swarms) — enterprise swarm orchestration (hierarchical/parallel/graph), Apache-2.0.
- [Fetch.ai uAgents](https://github.com/fetchai/uAgents) — blockchain-integrated autonomous agents with on-chain payments (Agentverse).
- [DeerFlow (ByteDance)](https://github.com/bytedance/deer-flow) — LangGraph super-agent harness with Markdown skills + sandboxed execution. Full analysis: [deerflow-analysis.md](../orchestrators/deerflow-analysis.md).
- [DeepAgents (LangChain)](https://github.com/langchain-ai/deepagents) — planning + sub-agent harness. Full analysis: [deepagents-analysis.md](deepagents-analysis.md).
- [Flue (Astro)](https://github.com/withastro/flue) — durable, sandboxed TypeScript agent framework from the Astro team; **1.0 Beta** (~2026-06-16, Apache-2.0, [flueframework.com](https://www.flueframework.com)). Harness-first model on the **Pi** agent loop (via `@flue/runtime`): **Durable Streams** record every prompt/tool-response/model-choice to an append-only log, so a fresh process resumes from the last checkpoint after a crash or provider timeout. Ships a **just-bash** in-memory sandbox (no Docker/VM) plus a `local()` sandbox; MCP-native and model-agnostic; **channels** ingest events from Slack/Teams/Discord/GitHub/Linear; on Cloudflare Workers each agent becomes a Durable Object (SQLite FS, `runFiber`/`stash`/`onFiberRecovered`). Supports **subagents / task delegation** (swarm-style coordination is not documented in first-party sources); `SuperagenticAI/pyflue` is a community Python port, not first-party.
- [Fractal (Plasma)](https://github.com/plasma-ai/fractal) — hierarchical, recursive multi-agent orchestrator: each node runs an assigned coding agent (Claude Code, Codex, Grok Build, OpenCode, Oh My Pi) inside its own **git worktree**, iterating toward a goal and autonomously spawning child nodes for separable subtasks, bounded by hard limits on iterations/nesting depth/child-count/cost/runtime; a local SQLite DB tracks cost and run metadata via a terminal UI. Nodes run **without permission prompts by default** — the docs explicitly warn to launch only tasks you'd trust unsupervised (Apache-2.0; PyPI `plasma-fractal`; 772★, `gh api` 2026-09-24).
- [multica](https://github.com/multica-ai/multica) — source-available platform (modified Apache 2.0: no third-party hosted-service/resale + a frontend logo clause — not OSI open-source) that turns coding-agent CLIs into managed teammates: create issues → assign to an agent or a squad, a local daemon executes and streams progress over WebSocket, with autopilot (cron/webhook) scheduling and a reusable skill library. Integrates 13 agent CLIs (Claude Code, Codex, GitHub Copilot CLI, OpenClaw, OpenCode, Hermes, Gemini, Pi, Cursor Agent, Kimi, Kiro CLI, Antigravity, Qoder CLI); Go + Postgres 17/pgvector backend, Next.js 16 UI. Install `brew install multica-ai/tap/multica` or the `install.sh` script; CLI flows `multica login` → `multica daemon start` → `multica issue create` / `multica workspace switch`. Auth is browser-based via `multica login` — no env vars documented.
- [sudocode](https://github.com/sudocode-ai/sudocode) — git-native agent orchestrator (Apache-2.0, verified from LICENSE; TypeScript): human requirements live as version-controlled **specs**, agent runtime context as **issues**, linked bidirectionally (blocks / related / parent-child / discovered-from) and persisted as JSONL committed to git with a local SQLite cache. Runs Claude Code / Codex / Cursor (+more via Agent Client Protocol, added v0.1.19) in parallel with dependency-ordered (topological) execution and a kanban-style real-time UI. `npm install -g sudocode`; ships CLI + local server/UI + MCP server. v0.2.0 (2026-03-18); 287★, last push 2026-03-18 (`gh api`, 2026-07-23). Directly comparable to multica above (multi-CLI, issue-driven, local daemon) — sudocode is git-repo-resident and OSS where multica is a source-available managed platform.
- [Runtype](https://runtype.com/) — hosted AI product development platform to build, test, deploy and monitor AI capabilities in user-facing products ([docs][runtype-what-is]). **Flows** are sequential, step-typed workflows (prompt / transform / conditional / loop / fetch-url / record steps); **Agents** autonomously select tools and sequence calls; both are versioned, publishable, and manageable as code. **Products** bundle Flows/Agents/Records/Tools and expose them through **Surfaces** — chat widget, REST API (auto-generated OpenAPI), Slack, Discord, email, SMS, iMessage, webhook, Chrome, MCP server, and Agent-to-Agent (A2A) ([docs][runtype-surfaces]). **Evals** compare model/prompt configurations against shared test inputs; execution logs and an audit trail support debugging. Model access is platform keys (no provider account needed) or **BYOK**, multi-provider (OpenAI, Anthropic, Google, xAI, …) (vendor site, 2026-09-24). **Claude Code integration**: `npx -y @runtypelabs/cli@latest onboard` configures a hosted MCP server (`https://api.runtype.com/v1/mcp/protocol`, Standard and Code-Mode variants) for Claude Code, Cursor, Codex, Gemini CLI, OpenCode and VS Code, installing Claude Code skills and completing OAuth via `claude mcp login runtype` ([docs][runtype-coding-agents]); a Claude Desktop `.mcpb` extension is offered separately ([docs][runtype-mcp-server]). **Self-hosting (BYOC)** requires the Enterprise plan: exported Flows/Agents run via the `@runtypelabs/runtime` package on Cloudflare Workers, Google Cloud Run, Node.js or Vercel, but model execution, memory, crawling, email and search still call back to the hosted platform ([docs][runtype-self-hosting]). **Pricing** (billing page, 2026-09-24): Launch is free ($0 pay-as-you-go, 14-day trial, $5 signup credit, no BYOK); Team is $399/mo or $3,999/yr with BYOK and $50/mo rollover inference credits; Enterprise is custom-priced and adds self-hosting/SLA ([docs][runtype-billing]). Licence / open-source status of the core platform is **not stated in first-party docs (checked 2026-09-24)**; the GitHub org [`runtypelabs`](https://github.com/runtypelabs) publishes satellite projects (`skills`, `persona`) rather than the platform itself, and the `@runtypelabs/cli` onboarding package is separately listed Apache-2.0 on npm (checked 2026-09-24) — that covers only the CLI, not the hosted platform; `@runtypelabs/runtime` (the BYOC export package referenced in the self-hosting docs) is not published on the public npm registry (404, checked 2026-09-24), so no licence could be checked for it either.

**Runtype harness satellites** (checked 2026-09-30; both MIT per their `LICENSE` files, `gh api`).
[`hermes-runtype-otel`][runtype-hermes-otel] is a Hermes Agent plugin that exports one OpenTelemetry
trace per agent turn to Runtype over OTLP/HTTP: an `invoke_agent` span, a `chat` span per model request
and an `execute_tool` span per tool call, collected through Hermes plugin observer hooks in both the CLI
and the gateway. It is a read-only mirror of `packages/hermes-adapter` in Runtype's monorepo (0★, pushed
2026-09-28). Content capture is off by default (IDs, model names, token usage, timings and status only),
and `RUNTYPE_OTEL_ENDPOINT` points it at any OTLP/HTTP traces URL. Its README states the limits: a trace
covers one turn, not a whole session; auxiliary model calls and subagent internals are excluded; and on
Hermes v0.21.4 a terminal provider error can hold a turn's trace until process exit (5-second flush
budget, leftovers dropped). [`persona`][runtype-persona] (249★, pushed 2026-09-28) is a VanillaJS AI chat
widget (`@runtypelabs/persona`) with WebMCP page tools, tool-call visualization and approval gates for any
SSE backend. It is a UI layer rather than a harness, so it is not scored.

- [Archon (coleam00)](https://github.com/coleam00/Archon) — "the first open-source harness builder for AI coding" (MIT, 23,585★/3,490 forks, pushed 2026-09-27, `gh api` 2026-09-30): a workflow engine that encodes a development process — plan, implement, validate, review, PR — as YAML nodes (`prompt` / `bash` / `loop` / human-approval gates) run by Claude Code (`CLAUDE_BIN_PATH`-configurable). Each run gets its own isolated git worktree so parallel fixes don't collide; a web console (`archon serve`) lists runs with an event log and artifacts, and workflows are defined once in `.archon/workflows/` and committed to the target repo. Pitched explicitly against "every run is different" LLM variance: "Repeatable — same workflow, same sequence, every time." **Rubric** (scored 2026-09-30, [README](https://github.com/coleam00/Archon#readme)): Shared: partial (CLI, Web UI, Slack, Telegram and GitHub can all trigger the same workflows, but no concurrency/locking semantics are documented); Distributed: no data (single-host CLI/server; no clustering documented); Reproducible: partial (the *workflow structure* — phase order, validation gates — is deterministic and stated as such; the AI steps inside each phase remain model-driven and are not pinned to a model or seed); Adaptable: yes (workflows are user-authored YAML mixing deterministic bash/git nodes with AI nodes); Versionable: yes (workflows live in `.archon/workflows/` and are committed to the target repo's own git history); Traceable: yes (the Web UI's Run detail page keeps "Event log, artifacts, workflow graph" per run).
- [Paperclip (paperclipai)](https://github.com/paperclipai/paperclip) — "the open-source app everyone uses to manage agents at work" (MIT, 94,913★/16,112 forks, pushed 2026-09-30, `gh api` 2026-09-30): a Node.js server + React UI that runs an org chart of agents (any provider — OpenClaw [see the OperatingSystem-1 entry below], Claude Code, Codex, Cursor, bash, HTTP) against ticketed tasks, with per-agent monthly budgets, heartbeat scheduling, and multi-organization data isolation on one deployment. Its own framing: "If OpenClaw is an employee, Paperclip is the company." **Rubric** (scored 2026-09-30, [README](https://github.com/paperclipai/paperclip#readme)): Shared: yes (an org chart is a shared task/ticket store that multiple agents and human managers read and act on); Distributed: partial (coordinates heterogeneous agents/runtimes remotely via heartbeats, but the control plane itself is described as one Node.js server — no clustering documented); Reproducible: no data (agent execution is model-driven; no pinned-version rebuild path documented); Adaptable: yes ("Bring Your Own Agent. Any agent, any runtime, one org chart"); Versionable: yes ("config changes are revisioned, and bad changes can be rolled back safely"); Traceable: yes ("Every conversation traced. Every decision explained. Full tool-call tracing and immutable audit log").
- [AX (google/ax)](https://github.com/google/ax) — "Google's open agentic orchestration runtime" (Apache-2.0, LICENSE file confirmed, 12,627★/615 forks, pushed 2026-09-27, homepage [agentexecutor.io](https://agentexecutor.io), `gh api` 2026-09-30): a Kubernetes-style declarative orchestrator (`Task` / `Workspace` / `Model` CRDs, `kubectl`-like `ax apply` / `ax watch` / `ax ssh`) for running large numbers of sandboxed agent workloads on a cluster. It runs on top of a separate sandboxing layer, [Agent Substrate](https://github.com/agent-substrate/substrate), and supports `ax suspend` / `ax resume` to checkpoint and later resume an idle agent exactly where it left off. The README's own warning: "AX and several of its features are in heavy development... will likely introduce major breaking changes prior to a stable release." A "Celesto critique" of AX was requested for this research batch but not found: two web searches surfaced only unrelated hits (a same-named but unconnected sandboxing project, `CelestoAI/celesto`) — dropped as unverifiable rather than cited from a stand-in. **Rubric** (scored 2026-09-30, [README](https://github.com/google/ax#readme)): Shared: no data (no multi-user/multi-agent shared-store claim in the fetched docs — the primitives are per-task, not shared state); Distributed: yes (runs on a Kubernetes cluster with a control plane, Redis, and per-cluster billions-of-tasks scale, per the README's own architecture); Reproducible: partial (task/workspace/model definitions are declarative YAML, but the agent's own actions inside a sandbox are model-driven and not pinned); Adaptable: yes ("build your own runner image to replace the default", per the Runners doc); Versionable: partial (manifests are plain git-friendly YAML, but AX documents no built-in snapshot/diff/rollback of task state itself — `ax suspend`/`resume` is a checkpoint, not a version history); Traceable: partial (`ax watch`/`ax ssh` give live observability into a running task, but no citation or lineage mechanism is documented).
- [OperatingSystem-1 (Mitosis Labs) harness tools](https://github.com/OperatingSystem-1) — two small multi-agent coordination tools from the org behind the Cortex memory system ([mitosis-cortex-analysis.md](../context-memory/mitosis-cortex-analysis.md)). `mcp-git-coord` (its README's own "## License" section says MIT, but **no LICENSE file exists in the repo** — a contents listing shows none, and `gh api`'s `license` field is `null`, checked 2026-09-30 — treat as unlicensed per this corpus's citation rule) is an MCP server that lets multiple coding agents on the same repo register intent (`coord_register`), detect file-level conflicts before code is written, and resolve merges with full team context (`coord_merge_check` / `coord_merge_resolve`); a companion `.mi/` context-cache layer stores pre-built per-directory architecture notes so a fresh session skips re-exploration. `openclaw-operator` (Apache-2.0) is a Kubernetes operator for the OpenClaw AI-agent platform — **it is a fork of [stubbi/openclaw-operator](https://github.com/stubbi/openclaw-operator)** (400★ on the original vs. 0★ on the Mitosis Labs fork, fork last pushed 2026-05-13, `gh api` 2026-09-30), so it is not original OperatingSystem-1 work. This is the same OpenClaw platform [goclaw-analysis.md](../infrastructure/goclaw-analysis.md) describes GoClaw as reimplementing in Go ("OpenClaw rebuilt in Go," per that doc; confirmed against [openclaw.ai](https://openclaw.ai)'s own description of a single platform spanning both messaging channels — Telegram/Discord/WhatsApp/Signal/Slack/iMessage — and coding-workflow integrations, 2026-09-30) — not a separate product. **Rubric** (scored 2026-09-30, `mcp-git-coord` only — the operator is a dormant fork, not scored as OperatingSystem-1's own work): Shared: yes (`coord_register` / `coord_active` coordinate multiple agents' intent on one repo, per the README's own worked examples); Distributed: no data (coordination state lives in the repo the agents already share via git; no separate sync service is documented); Reproducible: n/a (a coordination protocol, not a state-rebuild target); Adaptable: partial (works with any MCP-compatible tool, but the `.mi/` schema and hook set are fixed); Versionable: no data (coordination state is ephemeral session registration, not itself versioned — though it operates on top of git); Traceable: partial (`coord_merge_check` explains *why* a conflict exists with team context, but there is no persistent audit log of past merges).
- [DeepSeek Harness (dsh)](https://github.com/deepseek-ai/deepseek-harness) — full profile: [deepseek-harness-analysis.md](../coding-agents/deepseek-harness-analysis.md); cross-ref: [CC-harnessrouter-analysis.md](../../cc-community/CC-harnessrouter-analysis.md) already names DSH among the harnesses it unifies. Additions confirmed first-party since that profile (`gh api`/repo fetch, 2026-09-30): the underlying [Cordis](https://github.com/cordiverse/cordis) DI framework's "spatiotemporal composability" paper is now independently fetched rather than cited only from dsh's own README (arXiv:2608.25512, MIT, 8,923★); the repo's `.agents/notes/{proposed,implemented,rejected,archived}` directory tree is a real, structurally-confirmed agent-written decision-record practice — a rejected proposal is kept on file specifically while its rationale "prevents a tempting, meaningful mistake" (`.agents/notes/README.md`, verbatim), so a later agent that rediscovers the same idea meets the reason it died instead of relitigating it.

Design lens — Lindenberg's *Everything Is a Plugin, Proven* reads this decision-record discipline, not the plugin architecture itself, as the transferable practice: once a team accepts its codebase "is developed primarily by coding agents," the consequence is that "agents follow enforced gates far more reliably than prose conventions," so review conventions get encoded as exit codes and rejected ideas carry their own falsifying evidence rather than being re-litigated (Lindenberg, *Everything Is a Plugin, Proven*, LinkedIn, 2026-08-15; `linkedin.com/pulse/everything-plugin-proven-andré-lindenberg-gamle`).

## 2. LLM Orchestration & Routing

- [LangChain](https://github.com/langchain-ai/langchain) — broad LLM app framework, 100+ integrations (MIT).
- [Haystack (deepset)](https://github.com/deepset-ai/haystack) — production RAG/pipeline framework (Apache-2.0).
- [DSPy (Stanford)](https://github.com/stanfordnlp/dspy) — "programming, not prompting": modules + optimizers auto-tune prompts/weights; v3.1 (Jan 2026), Agenspy adds MCP/A2A.
- [Restack](https://github.com/restackio) — event-driven, durable agent backend with task queues (Apache-2.0).
- **Routers, gateways & aggregators** now live in a dedicated catalog → [llm-routers-gateways-landscape.md](../infrastructure/llm-routers-gateways-landscape.md) (29 provider-agnostic tools: OpenRouter, Withmartian/Martian, LiteLLM, Portkey, Mammouth, Requesty, Helicone, Vercel/Cloudflare AI Gateway, OpenRouter Fusion, …). CC-side routing config: [CC-model-provider-configuration.md](../../cc-native/configuration/CC-model-provider-configuration.md).
- [Intent-Router (angel291592)](https://github.com/angel291592/Intent-Router) — an **intent compiler**, not a router itself: a Claude Code/Codex/OpenCode/Cursor skill (`npx skills add angel291592/Intent-Router`; no install, API key, or dependency) that converges a vague request into a typed `IntentSpec` — probing what the repo, ticket system, or docs already answer, asking only the one question no file can resolve, and halting on a contradiction, a dual reading, or an unproven premise — before handing off to "your planner / agent / workflow / human." Its own framing: [Jev](../infrastructure/jev-analysis.md) and Laya (System-1 decision models — see [system-1-decision-models-landscape.md](../reference/system-1-decision-models-landscape.md)) "turn an *already-clear* input into a typed, calibrated decision"; Intent-Router is the **upstream layer** that produces that clear input to begin with. Every run writes a cross-session artifact, `.intent/<intent>.intent.yaml`, carrying evidence pointers per resolved field and its own state (waiting on a question / settled / already checked); a later session reads that file before probing anything, and the check of delivered work against the spec is written back into the same file. Self-reported evals (same-author replay, not independently verified): an N=5-bare vs. N=3-with-skill delivery comparison (2026-09-24) where every skill-assisted run asked exactly the one question that mattered and all 3 stated a failure policy, vs. none of the 5 bare runs; a separate 10-case suite held 8/10 with "0 hallucinated evidence" on the same date. MIT (LICENSE-confirmed, `gh api` 2026-09-30); 411★/47 forks, v1.2.0 (2026-09-27).

## 3. Lightweight & Specialized Frameworks

- [Atomic Agents](https://github.com/BrainBlend-AI/atomic-agents) — modular Pydantic/Instructor pipelines with strict I/O schemas.

## 4. Agent Memory Infrastructure

Non-CC memory frameworks; for memory tools that integrate *with Claude Code* (MemSearch, Claude-Mem, MemPalace, ByteRover) see [CC-community-tooling-landscape.md](../../cc-community/CC-community-tooling-landscape.md).

The field has reframed memory as **context engineering** — assembling persistent, evolving state across sessions rather than just enlarging the context window.

- [Graphiti (Zep)](https://github.com/getzep/graphiti) — real-time temporal knowledge-graph engine; P95 ~300ms hybrid (vector + BM25 + graph) retrieval, MCP server, Apache-2.0.

- [MemoryOS](https://github.com/BAI-LAB/MemoryOS) — hierarchical short/mid/long-term memory OS for personalized agents; +49.11% F1 over baselines on LoCoMo (self-reported), EMNLP 2025 Oral (Apache-2.0).

PydanticAI-based; ships an MCP server (`ace-mcp`) and a Claude Code runner. Offline benchmark-driven counterpart: autoharness (§3).
- [learnings-ralphy (qte77 estate)](https://github.com/qte77/learnings-ralphy) — **file-based compound-learning memory**, the filesystem-as-memory complement to the graph/vector engines above: plain-Markdown `CLAUDE.md` + `AGENT_LEARNINGS.md` / `LEARNINGS.md` as durable, git-versioned agent memory with an explicit promotion path (inline fix → `AGENT_LEARNINGS.md` → always-loaded `.claude/rules/` → skills). `learnings-ralphy` distills these **across the whole repo estate** on a weekly loop (synthesize → PRD → TDD → write-back PR). - [exxperts (EXXETA)](https://github.com/EXXETA/exxperts) — local-first agent app with **governed, approval-gated memory**: candidate memories are proposed after a conversation and must be explicitly approved before they're saved; approved notes are timestamped, traceable to their source conversation, and user-editable; data stored as plain local files, with an opt-in remote mode limited to paired devices. Works with any model provider (Claude, ChatGPT, Gemini, Mistral, local); built-in MCP tools + web search; desktop apps (macOS/Windows) + web + CLI; Community Edition OSS, Enterprise forthcoming (Apache-2.0; 357★, `gh api` 2026-09-24).
- [IWE](https://github.com/iwe-org/iwe) — turns a directory of plain Markdown notes into a queryable knowledge graph without moving content into a database: notes link via hierarchical inclusion + cross-references, an LSP server gives IDE-like search/autocomplete/rename-with-link-updates (VS Code, Neovim, Zed, Helix), and an MCP server (`iwec`) + CLI expose the same search/retrieve/create/refactor operations to Claude Code, Cursor and other AI tools; agent writes are checked against declared scope, frontmatter schemas, and graph integrity. Rust; claims 20,000 files/sec (Apache-2.0; 1.7k★, `gh api` 2026-09-24).
- [LightMem](https://github.com/zjunlp/LightMem) — lightweight memory-augmented generation framework (**ICLR 2026**): pre-compression (e.g. LLMLingua-2), topic segmentation, threshold-gated memory extraction, and hybrid embedding+context retrieval, with pluggable storage/retrieval backends and cloud (OpenAI, DeepSeek) or local (Ollama, vLLM) models. On LoCoMo with GPT-4o-mini the repo self-reports ~74% accuracy at lower token/latency cost than Mem0 and A-MEM (MIT; 1.2k★, `gh api` 2026-09-24).
- [Maximem Synap](https://github.com/maximem-ai/maximem_synap_sdk) — production memory layer for agents with 20+ framework integrations (LangChain, CrewAI, LlamaIndex, AutoGen, OpenAI Agents, Google ADK, Pydantic AI, Semantic Kernel, Haystack, …); self-reports 92% on LongMemEval and 93.2% on LOCOMO. The SDK (Python/JS) is an open, Apache-2.0 client only — the Synap memory engine itself is a **closed, hosted cloud service** requiring a Maximem API key, per the repo's own README (`gh api` 2026-09-24).
- [Agent Zero Memory: Provenance-Aware Long-Term Memory for LLM Agents](https://arxiv.org/abs/2608.29606) — Wu & Zhu (arXiv:2608.29606, 2026-08-30) integrate three parallel memory structures — an episodic event timeline, an entity-event knowledge graph, and a hierarchical documentary memory of curated facts — retrieved via intent-gated, source-routed concurrent search over hybrid embedding + lexical indexes. Every stored item carries origin/timestamp/evidence-pointer provenance, and every answer is generated under a "citation lock." Self-reports 95.60% on LongMemEval and 93.60% on LoCoMo — comparable to Maximem Synap above — with the paper stating "near-state-of-the-art quality at up to 20× lower cost per query, the signature of memory-driven, rather than model-driven, quality" (paper claims; methodology not independently verified; no GitHub/HuggingFace/project link found in the abstract or paper body as of 2026-09-24).
- [MemMachine](https://github.com/MemMachine/MemMachine) — open-source universal memory layer across three layers: working memory (immediate context), episodic memory (conversational history in a **Neo4j** graph), and profile memory (user facts in SQL). Python SDK, REST, TypeScript, MCP server; integrates LangChain, LangGraph, CrewAI, LlamaIndex, AWS Strands, n8n, Dify, FastGPT; self-hosted, Docker, or managed cloud (Apache-2.0; 3.2k★, `gh api` 2026-09-24).
- [Memento](https://github.com/Memento-Teams/Memento) — memory-augmented continual learning for LLM agents that improves via **experience replay instead of fine-tuning**, framed as online RL over a memory-augmented MDP: a planner retrieves relevant past trajectories from a "Case Bank" via case-based reasoning, an executor runs subtasks through MCP tools, and both successful and failed trajectories are logged back for future retrieval. Repo self-reports 87.88% (val, Pass@3 top-1) / 79.40% (test) on **GAIA** ([paper](https://arxiv.org/abs/2508.16153)). Renamed from `Agent-on-the-Fly/Memento`; last push 2025-10-05 (MIT; 2.6k★, `gh api` 2026-09-24).
- [Memorable](https://www.memorable.sh/) — **procedural, graph-based** agent memory, contrasted by the vendor with RAG's text-chunk retrieval: captures successful agent runs as reusable "procedures" (steps with a precondition/postcondition/outcome), assembling them into a graph via shared steps and prefixes so agents can compose and discover workflows (~60ms recall, three matching strategies). CLI, dashboard, JSON ingestion API, read-only MCP server; local files, `gbrain`, or self-hosted Postgres. The vendor's site quotes Y Combinator's Launch page listing it as "**Memorable (YC S27)**" (vendor site, 2026-09-24).
- [Metis (MemTensor)](https://github.com/MemTensor/Metis) — a **memory foundation model**: rather than an external retrieval layer, Metis Blocks are inserted into transformer layers (a Local Memory Block holding a persistent memory matrix + a Hyper Memory Block using a Gated Delta Network) so the model compresses history into native memory and updates it via gradient-free forward passes at inference, weights frozen ([paper](https://arxiv.org/abs/2607.26760), arXiv:2607.26760). First entry in a planned model series. **Non-commercial only**: paper is CC BY-NC-SA 4.0, repo code is PolyForm Noncommercial 1.0.0 (verified from the LICENSE file, `gh api` 2026-09-24); 165★.
- [Neo4j Agent Memory (neo4j-labs)](https://github.com/neo4j-labs/agent-memory) — graph-native memory across short-term (session messages), long-term (entity graph + preferences via the POLE+O model), and reasoning (decision traces / tool-use audit trail) layers, backed by Neo4j; multi-stage entity/relationship extraction (spaCy, GLiNER, LLM, GLiREL) with optional Wikipedia/Diffbot enrichment. Python + TypeScript SDKs; hosted service, MCP server, or self-hosted Neo4j. An experimental **Neo4j Labs** project — community-supported, not official Neo4j (Apache-2.0; 562★, `gh api` 2026-09-24).
- [Reef (Human-Agent Society)](https://github.com/Human-Agent-Society/reef) — infrastructure connecting agent inference, feedback, learning and versioned delivery in one loop (Serve → Observe → Grow → Commit): interactions are served and recorded, feedback is matched back to them, eligible records generate updates, and updates are evaluated before being published to a versioned history. Supports evolving either model weights (via a GPU training stack, e.g. Slime) or the agent harness (prompts/rules/skills, model-endpoint only). Very new — created 2026-08-31 (Apache-2.0; 4.5k★, `gh api` 2026-09-24).
- [HydraDB](https://github.com/hydra-db/hydradb) — an object-store-native distributed graph database that disaggregates storage from compute: the graph, its write-ahead log, and its traversal indexes live only in S3-compatible object storage (~$0.023/GB-mo, vs. $65–146/GB-mo for the RAM most graph databases require, per the project's own [blog][hydradb-blog]); query nodes and indexer workers hold only disposable, rebuildable local caches. A single active writer per cell is elected with a compare-and-swap lease on the bucket itself, fenced by write epochs from [SlateDB][slatedb] (already in production at Dropbox); reads speak standard Neo4j Bolt, and traversal runs through SuiteSparse GraphBLAS. Named target workloads: ontologies, agent memory, and "company brains" fed by live Slack/Notion/GitHub/Gmail connectors (AGPL-3.0, 13,017★, `gh api` 2026-09-30). Contrast with [Omnigraph](#agent-native-graph--hybrid-rag-platforms) (§7 below) — a different bet on the same shared-graph-under-concurrent-writers problem, using Git-style branch/merge instead of a single elected writer per cell. **Rubric** (scored 2026-09-30, [README][hydradb]/[blog][hydradb-blog]): Shared: yes (multiple writers target the same object-store-backed graph, serialized through the per-cell CAS lease rather than a single-writer assumption); Distributed: yes (storage/compute disaggregation with independently-scaling query and indexer tiers against one durable object store, per the architecture diagram); Reproducible: partial (indexer-built CSC generations are rebuilt deterministically from the durable WAL/manifest state, but no pinned-version or bit-identical-rebuild claim is documented); Adaptable: no data (no plugin/extension-point documented beyond swapping the object-storage backend); Versionable: no data (WAL/SST durability, not a documented snapshot/diff/rollback of graph state); Traceable: no data (write epochs fence stale writers but are not exposed as a citation or audit-trail feature).

Design lens — Lindenberg's *The Graph Doesn't Need RAM Anymore* frames HydraDB's bet as: once the RAM bill stops forcing retention limits, "keeping every relationship, every version, every invalidated fact stops being a compromise and becomes the default" — directly on the **Shared**/**Distributed** properties this catalog tracks (Lindenberg, *The Graph Doesn't Need RAM Anymore*, LinkedIn, 2026-09-12; `linkedin.com/pulse/graph-doesnt-need-ram-anymore-andré-lindenberg-kqwde`).

`scored 2026-09-30`

- [MemoryWAM](https://github.com/yangsizhe/MemoryWAM) — an **embodied/robotics-vision** persistent-memory mechanism, distinct in kind from the LLM-conversational/session memory tools above: a video-DiT + action-DiT dual-arm manipulation policy conditions on long, non-Markovian task histories via a hybrid cache (sliding-window recent frames + event-boundary anchor frames + compact learnable "gist tokens"), cutting inference complexity from O(N) to O(N/d) vs. keeping the full history (Apache-2.0, verified via `gh api` license lookup; [paper](https://arxiv.org/abs/2606.20562), arXiv:2606.20562, 2026-06-18). Evaluated on RMBench across nine dual-arm manipulation tasks; 55★, project-page-style repo (no training codebase) as of 2026-07-23.
- [Marginal Advantage Accumulation (MAA)](https://arxiv.org/abs/2606.20475) — offline memory-curation method for LLM-agent self-evolution (Alibaba International Digital Commerce Group; arXiv:2606.20475, 2026-06-18): accumulates signed evidence per memory operation across batches of experience traces (semantic-identity merging + baseline-differenced signals + EMA) so a persistent skill/memory bank keeps only robustly-effective operations, without live environment rollouts. Best result in 14/16 settings across 4 datasets × 4 target models, and beat the online SkillOpt baseline on the two strongest models; reports ~75% lower optimization-phase token cost than online methods (paper claims; methodology not independently verified; no code release found).
- [Does Your Agent's Memory Survive a Model Upgrade? A Controlled Study of Memory Portability](https://arxiv.org/abs/2609.05339) — Goyal & Ray (arXiv:2609.05339, 2026-09) compare four memory representations across model-upgrade migrations: **LC-RAW** (verbatim history), **RAG** (chunked retrieval), **NOTES** (LLM-compressed summaries), and **KG-fixed** (schema-normalized knowledge graphs). Fixed-schema KGs are the most stable; NOTES shows high model coupling (accuracy swings of +9.91 to −13.28 pp depending on migration direction); RAG failures are dominated by retrieval breakage (81% of the deficit) rather than generation (paper claims; methodology not independently verified).
- [On the Fragility of Self-Improving Agents: Variance, Task Order, and Underspecification](https://arxiv.org/abs/2608.18066) — Ye, Li, Pruksachatkun, Zhang & Wu (arXiv:2608.18066, 2026-08; code/dataset links in the paper point to Salesforce AI Research) find memory-based self-improving agents highly sensitive to evaluation noise and to task ordering — prior work's default task order acted as a hidden curriculum masking true reliability — and trace much of the remaining fragility to task/environment underspecification; detailed rubrics and feedback help but leave a persistent gap. Recommends multi-run, order-varied evaluation protocols (paper claims; methodology not independently verified).
- [HarnessEvolve: Learning from Reference Trajectories for Reliable Agent Self-Evolution](https://arxiv.org/abs/2609.00829) — Jiang, Chu, Tian, Zhang, Yang, Yang, Liu, Lv & Li (arXiv:2609.00829, 2026-09-01) target three self-evolution failure modes — **credit-assignment failure** (terminal-only success/failure feedback leaves the error step ambiguous), **shortcut learning** (agents memorize task-specific patterns instead of generalizable capability), and **catastrophic forgetting** (unguarded updates degrade prior competence) — by decoupling execution from optimization: reference trajectories generated from ground-truth answers localize error signals and cluster failure patterns, gated by a quality gate (filters data leakage) and a performance gate (blocks updates that regress current or recently-learned performance). A reliability-focused complement to MAA and the fragility study above (paper claims; methodology not independently verified; no GitHub/HuggingFace/project link found in the abstract or paper body as of 2026-09-24).
- [AgentiCow](https://github.com/ruvnet/agenticow) — "Git for Agent Memory": copy-on-write branching for an embedded vector store. Branching a base memory of any size costs ~0.5ms/162 bytes (flat, independent of base size); a branch reads through to `parent ∪ own edits` with the child winning collisions; `checkpoint`/`rollback` and `diff`/`promote` give a Git-style workflow (branch → test → reviewed → production) for per-agent or per-user personalization off one shared base (MIT; 52★/8 forks, `gh api` 2026-09-30). Same author (ruvnet) as RuVector, a J3 decision-model lead tracked separately in #517. Last push 2026-07-04 (`gh api` 2026-09-30) — quiet for about 3 months. **Rubric** (scored 2026-09-30, [README](https://github.com/ruvnet/agenticow#readme)): Shared: yes ("parallel agents share one base memory"); Distributed: no (single embedded file, no sync/remote server documented); Reproducible: yes (deterministic copy-on-write reads, no LLM in the path); Adaptable: no data (no schema/backend extension points documented); Versionable: yes (branch/checkpoint/rollback/diff are explicit version-control primitives); Traceable: partial (`diff` reports added/overridden/tombstoned ids — a write-lineage trail, not answer citations).
- [Beads / bd (gastownhall)](https://github.com/gastownhall/beads) — Dolt-backed distributed graph issue tracker built as persistent structured memory for coding agents: a dependency-aware graph (`bd ready`/`bd create`/`bd dep add`) replaces markdown TODO lists, with `bd remember`/`bd prime` for durable project facts and `bd show <id>` for "task details and audit trail" (its own README's phrase). `bd dolt push`/`bd dolt pull` sync the underlying [Dolt](https://github.com/dolthub/dolt) database — a version-controlled SQL store with cell-level merge and native branching — across machines and agents; hash-based IDs avoid merge collisions in multi-agent/multi-branch workflows. `bd setup <agent>` wires into Claude Code, Codex, Factory.ai Droid, Cursor and more (MIT; 27,518★/1,868 forks, `gh api` 2026-09-30). Compare with `sudocode` (§1): both are git-native, multi-CLI agent trackers, but sudocode persists issues as JSONL committed to git with a local SQLite cache, where Beads persists them in a Dolt SQL database with its own branch/merge/remote-sync protocol. **Rubric** (scored 2026-09-30, [README](https://github.com/gastownhall/beads#readme)): Shared: yes (multi-agent claim + collision-free hash IDs); Distributed: yes (`bd dolt push`/`pull` to "other machines and agents," per the README's own architecture diagram); Reproducible: yes (Dolt is commit-addressed — the same commit rebuilds the same state); Adaptable: yes (typed graph links — `relates-to`/`duplicates`/`supersedes`/`replies-to` — plus hierarchical epic/task/sub-task IDs and pluggable per-agent setup); Versionable: yes (Dolt branching/diff/merge is version control for the data itself); Traceable: yes ("`bd show <id>` — View task details and audit trail," verbatim from the README).
- [Weighted Memory Tree (WMT)](https://arxiv.org/abs/2608.20631) — Dao, Kathalkar & Eaton (arXiv:2608.20631, 2026-08-21) organize an LLM agent's execution history into a hierarchy of tasks, subtasks and actions, each carrying a dynamic retention score updated by event-based modification and selection-based decay, so the memory "preserve[s] useful information, fold[s] completed trajectories, [and] suppress[es] low-utility content" instead of growing linearly. Self-reports a 9.97-point accuracy gain and 32.8% lower prompt-token usage vs. linear memory, plus memory-poisoning experiments showing WMT limits how long unreliable information persists (paper claims; methodology not independently verified; no code repository found as of 2026-09-30). **Rubric** (scored 2026-09-30): Shared: n/a (single-agent research method, no shared-store claim); Distributed: n/a (no deployment described); Reproducible: no (no code/repo link found); Adaptable: no data; Versionable: no data; Traceable: no data.
- [JITMEM: Just-in-Time Memory](https://arxiv.org/abs/2609.27334) — Zhou, Li, Liu, Yavuz & Joty (arXiv:2609.27334, 2026-09-23; billed as Salesforce AI Research per the lead that queued it — the abstract page itself states no author affiliation) defer memory curation from write-time to read-time: raw trajectories are kept as-is, and a curator synthesizes a compact, task-adaptive summary only once a new task's need is known, sidestepping the long-horizon credit-assignment problem that comes with deciding what to keep before future queries exist. Self-reports absolute success-rate gains of 16.2/16.3/3.9 points over the strongest baselines on ALFWorld/WebShop/τ²-bench respectively (paper claims; methodology not independently verified; no code repository found as of 2026-09-30). **Rubric** (scored 2026-09-30): Shared: n/a (single-agent research method, no shared-store claim); Distributed: n/a (no deployment described); Reproducible: no (no code/repo link found); Adaptable: no data; Versionable: no data; Traceable: no data.
- [lossless-memory (aru-labs)](https://github.com/aru-labs/lossless-memory) — deliberately the opposite design from the summarization/embedding engines above: "never summarize, keep every line, and put a timestamp on everything." Every turn becomes a fixed seven-field record (`ts`/`actor`/`role`/`type`/`text`/`model`/`session`) appended to a per-day JSONL file, which is the sole source of truth; a SQLite FTS5 + `sqlite-vec` index is a derived, fully rebuildable cache. Its "Temporal Backbone" parses time phrases ("yesterday evening," "3 days ago," English and Japanese) into a range *before* ranking, so time-scoped queries return verbatim chronological lines rather than a semantically-similar paraphrase; semantic search is the fallback, not the default. A small "LLL" topic-marker index is injected into context every turn so identity survives compaction. Explicitly single-user, single-machine, no server/cloud, and the README states plainly: "There are no published benchmarks" (MIT; 133★/11 forks, `gh api` 2026-09-30). **Rubric** (scored 2026-09-30, [README](https://github.com/aru-labs/lossless-memory#readme)): Shared: no ("designed for one person and one AI, running on one machine"); Distributed: no (same reason — no server, no cloud); Reproducible: yes ("every index below can be deleted and rebuilt from [the raw logs]. Nothing else is required to survive."); Adaptable: partial (a `config.json` timezone setting is the only documented extension point); Versionable: no data (plain append-only files are git-friendly, but the README documents no git-backed versioning feature); Traceable: yes (every record — utterance, action, document chunk — carries an explicit timestamp and session id).
- [Sumanth077/Hands-On-AI-Engineering](https://github.com/Sumanth077/Hands-On-AI-Engineering) — a 45-project worked-example collection (3,758★, no LICENSE file — `gh api` 2026-09-30 reports `license: null`, so cite as examples only, not adoptable code). Its `ai_agents/research_assistant_with_memory` folder is a memory-focused example, `ai_agents/agentic_rag_system` is an agentic-RAG example, `ai_agents/self_evolving_code_review_agent` and `ai_agents/multi_agent_coding_assistant` are harness/self-improvement examples (self-evolving review loop; multi-agent coding pipeline), and `ai_agents/grounded_document_agent` pipes LlamaParse's page-aware output (§7) into a local, citation-grounded PDF Q&A agent running on Ollama; no rubric scoring (it's a demo, not a product).

### GraphRAG family

- [Microsoft GraphRAG](https://github.com/microsoft/graphrag) — entity/relationship extraction → Leiden community detection → Global / Local / DRIFT search over community summaries (MIT, v3.2.0, ~36k★, `gh api` 2026-09-30). Indexing is compute-heavy; built for reasoning over large private corpora. Paper: [Edge et al. 2024, arXiv:2404.16130](https://arxiv.org/abs/2404.16130). The repo's own banner now states it is "largely in maintenance mode" and won't accept new features, only bug/CVE fixes ([README](https://github.com/microsoft/graphrag#readme)). **Rubric** (scored 2026-09-30, row G evaluation, [README](https://github.com/microsoft/graphrag#readme)): Shared: no data (a local indexing pipeline + query CLI; no multi-agent/multi-user access pattern documented); Distributed: no data (single-machine indexing pipeline; no cluster/sync docs found); Reproducible: no (entity/relationship extraction is LLM-driven with no pinned model or seed documented in the README — a fresh index over the same corpus is not guaranteed to match a prior one); Adaptable: partial (prompt tuning and a documented config-migration path between versions, but the extraction schema itself is fixed); Versionable: no (the README's "Versioning" section covers config-schema compatibility across GraphRAG releases via `breaking-changes.md`, not snapshot/diff/rollback of the indexed graph data itself); Traceable: no data (neither the README nor the docs site's [Local Search](https://microsoft.github.io/graphrag/query/local_search/) / [query overview](https://microsoft.github.io/graphrag/query/overview/) pages document a citation, data-reference or audit-log feature for query answers).
- [LightRAG (HKUDS)](https://github.com/HKUDS/LightRAG) — dual-layer KG + vector with five query modes (local/global/hybrid/naive/mix); positioned as an efficient GraphRAG alternative (MIT, v1.5.7, ~40k★, `gh api` 2026-09-30). **Rubric** (scored 2026-09-30, row G evaluation, [README](https://github.com/HKUDS/LightRAG#readme)): Shared: no data (a library/server for one deployment; no multi-agent concurrent-write semantics documented); Distributed: no data (Docker images and an API server are documented, but no clustering/sync protocol); Reproducible: partial (`ENABLE_LLM_CACHE` makes identical queries — same query, mode and model parameters — return identical cached results, and a documented `Reproduce.md` walks through reproducing the paper's evaluation numbers, but entity/relation extraction itself is LLM-driven with no default pinned model, so a from-scratch rebuild is not guaranteed deterministic); Adaptable: yes (pluggable KV/vector/graph storage backends, plus incremental updates and selective deletion without a full rebuild); Versionable: no (incremental updates change the KG in place; no snapshot, diff or rollback of graph state is documented — only Docker image tags for the software itself); Traceable: no data (README documents caches and reproduction steps but no citation/audit-trail feature for query answers).

- [RAPTOR](https://arxiv.org/abs/2401.18059) — recursive embed→cluster→summarize tree; retrieves across abstraction levels (MIT; ICLR 2024; paper reports +20% absolute on QuALITY with GPT-4).
- [nano-graphrag](https://github.com/gusye1234/nano-graphrag) — ~1,100-LOC hackable GraphRAG; swappable LLM/embedding/vector backends (Faiss/Neo4j/Ollama), async (MIT, ~3.9k★).
- [Graft (trailhq)](https://github.com/trailhq/Graft) — codebase context layer for coding agents (Claude Code, Cursor, Codex, Gemini, Copilot): a tree-sitter structural pass (23 languages, no LLM, ~3ms incremental refresh) extracts symbols/calls, then optional LLM enrichment groups them into typed-relationship (`depends_on`/`part_of`/`uses`/`implements`/`produces`) Markdown concept nodes with wikilinks the agent follows like docs; nodes are ranked by **in-degree coupling**, not PageRank. Repo self-reports 46% fewer tool calls, 42% fewer tokens, and +12pp on SWE-bench Verified (66% vs 54%) — not independently verified. Renamed from `NanoNets/Graft` to `trailhq/Graft` (MIT; 9.1k★, `gh api` 2026-09-24).

### Agent-native graph & hybrid RAG platforms

Graph-centric infrastructure built around agent access patterns (MCP, multi-agent branching, event-centric extraction) rather than the GraphRAG-pipeline shape above. - [SSTorytime (Mark Burgess)](https://github.com/markburgess/SSTorytime) — a "Semantic Spacetime" graph-database library over Postgres: a purpose-built N4L language and compiler turn plain-text notes into a knowledge graph (Go + Python APIs), with a companion [MCP-SST](https://github.com/markburgess/MCP-SST) proxy (unlicensed, 4★) for LLM/agent access. Point-in-time graph snapshots and a documented Agno multi-agent recipe — "One shared intelligence layer. All agents read and write to the same context graph" — directly target this arc's Shared/Reproducible/Traceable gap (MIT; 13,560★/1,543 forks, `gh api` 2026-09-30). **Rubric** (scored 2026-09-30, [README](https://github.com/semantica-agi/semantica#readme)): Shared: partial ("One shared intelligence layer. All agents read and write to the same context graph" — the Agno recipe shows the pattern working end to end, but, like Cognee's Company Brain pitch, the README documents no explicit concurrency/locking model for simultaneous writes); Distributed: partial (scales past a single process only by swapping to a distributed backend — Neptune/Neo4j for the graph store, Qdrant/Milvus/Pinecone for vectors — rather than a built-in sync/replication layer of its own); Reproducible: partial (the core reasoning engine is explicitly deterministic and LLM-free, but the optional extraction path uses an LLM with no documented pinned model or version, so a full end-to-end rebuild is not guaranteed identical); Adaptable: yes (RDF and LPG graph stores, and vector backends, are swappable "without touching your code"); Versionable: yes (`graph.state_at("2024-01-01")` point-in-time snapshots, listed in the README's own feature comparison as "Point-in-time graph snapshots" vs. "No" for compared alternatives); Traceable: yes (W3C PROV-O provenance on every fact, `trace_decision_chain()` full causal ancestry, and a "Registry" the docs describe as a "Live audit log of every graph mutation").

### Hybrid search & query transforms

- **BM25 + dense** — sparse keyword precision + dense semantic recall, fused via Reciprocal Rank Fusion or weighted combination.
- **Reciprocal Rank Fusion (RRF)** — rank-position-only fusion, default k=60 (Cormack et al., SIGIR 2009).
- [ColBERT (Stanford)](https://github.com/stanford-futuredata/ColBERT) — token-level late interaction (MaxSim); v2 adds residual compression; usable as retriever or reranker (MIT; [arXiv:2112.01488](https://arxiv.org/abs/2112.01488)).
- **HyDE** — the LLM drafts a hypothetical answer whose embedding retrieves real docs, bridging the query↔document vocabulary gap ([Gao et al. 2022, arXiv:2212.10496](https://arxiv.org/abs/2212.10496)); plus multi-query expansion and step-back prompting.

### Rerankers

- [Cohere Rerank](https://cohere.com/rerank) — cross-encoder rerank API (rerank-v4.0 pro/fast, 100+ languages); commercial.
- **Cross-encoders** — joint query+document forward pass (via sentence-transformers); higher accuracy than bi-encoders at O(n) per-candidate cost; run as a second stage after ANN retrieval. ColBERT (above) is the late-interaction middle ground.
- [bge-reranker-v2-m3](https://huggingface.co/BAAI/bge-reranker-v2-m3) — multilingual cross-encoder (BAAI, Apache-2.0); pairs with bge-m3 dense embeddings and is a strong default second stage after BM25+dense fusion.
- [Qwen3-Reranker](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B) — instruction-aware cross-encoder family (Alibaba, Apache-2.0; 0.6B/4B/8B, long context); the 0.6B is CPU-viable, larger sizes trade latency for quality.
- [mxbai-rerank](https://github.com/mixedbread-ai/mxbai-rerank) — DeBERTa-based cross-encoders in three sizes (mixedbread, Apache-2.0); a permissive-license alternative to bge-reranker.
- [FlashRank](https://github.com/PrithivirajDamodaran/FlashRank) — lightweight CPU reranker (Apache-2.0); bundles tiny cross-encoders (optional GGUF listwise) with no PyTorch dependency — for latency-sensitive post-retrieval.
- [rerankers](https://github.com/AnswerDotAI/rerankers) — unified Python API over cross-encoders, ColBERT, MonoT5, RankGPT, FlashRank and hosted APIs (answerdotai, Apache-2.0); swap backends without code changes, handy for A/B eval. [RAGatouille](https://github.com/AnswerDotAI/RAGatouille) makes ColBERT indexing + reranking practical in a few lines.
- **Hosted alternatives** (managed comparison points for local-first stacks): Voyage `rerank-2.5`, ZeroEntropy `zerank-2`, and Contextual AI `ctxl-rerank-v2` add instruction-following without fine-tuning (Contextual also ships open weights); Jina `reranker-m0` is multimodal (CC BY-NC). Per-search (Cohere) vs per-token (Voyage/ZeroEntropy) billing makes headline cost comparison non-trivial.

### Embedding models

- [SPECTER2](https://huggingface.co/allenai/specter2) — scientific-document embeddings (AllenAI; citation-proximity-trained, task-adaptive adapters), a strong default for scholarly-paper similarity where general-purpose embeddings underperform (Apache-2.0). SciNCL is a citation-neighbour-sampled alternative.
- General-purpose text embeddings (sentence-transformers bi-encoders, BAAI **bge**, **nomic-embed**) cover cross-domain corpora; prefer a domain-tuned model when the corpus is narrow (e.g. SPECTER2 for papers).

### Vector databases

- [Qdrant](https://github.com/qdrant/qdrant) — dense + sparse + multi-vector (ColBERT), built-in RRF/DBSF hybrid fusion, quantization (Apache-2.0, Rust).
- [Milvus](https://github.com/milvus-io/milvus) — cloud-native distributed; HNSW/IVF/DiskANN; billion-vector scale (Apache-2.0).
- [Weaviate](https://github.com/weaviate/weaviate) — vector + keyword + RAG in a single query; integrated auto-vectorization (BSD-3-Clause).
- [Chroma](https://github.com/chroma-core/chroma) — minimal API, in-memory → production (Apache-2.0).
- [pgvector](https://github.com/pgvector/pgvector) — vectors inside Postgres: ACID, JOINs, no separate system (PostgreSQL License).
- [Pinecone](https://www.pinecone.io/) — fully managed serverless ANN; no self-hosted option (proprietary).
- [LanceDB](https://github.com/lancedb/lancedb) — embedded, multimodal, Lance columnar format, zero-copy + versioning (Apache-2.0).
- [sqlite-vec](https://github.com/asg017/sqlite-vec) — vector search as a single-file **SQLite extension**; runs in-process and compiles to **WASM** for in-browser KNN, so precomputed embeddings can ship inside a static site with no server (Apache-2.0). Brute-force (no ANN index yet, pre-1.0) — fine at small/medium corpus sizes.

### RAG evaluation

- [RAGAs](https://github.com/explodinggradients/ragas) — reference-free metrics (faithfulness, answer relevancy, context precision/recall) via LLM-as-judge (Apache-2.0; [arXiv:2309.15217](https://arxiv.org/abs/2309.15217)).
- [TruLens](https://github.com/truera/trulens) — OTel tracing + LLM-as-judge feedback with agentic evaluators (MIT).

## 8. Output Validation, Guardrails & Verification

Validation is the post-generation sibling of retrieval (§7): enforcing that agent output conforms to a **schema/contract**, a **policy**, or **ground truth** before it is used. Tool facts (license, mechanism) verified first-party 2026-06-22. For the governance/threat-model framing (NIST AI RMF, OWASP LLM Top 10, MAESTRO) see [ai-security-governance-analysis.md](../../sdlc-lcm/ai-security-governance-analysis.md) and [mas-security-framework.md](../../sdlc-lcm/mas-security-framework.md).

### Structured-output / schema enforcement

- [Instructor](https://github.com/567-labs/instructor) — wraps any LLM call, validates the response against a Pydantic model, and re-prompts on validation failure (MIT). Thinnest provider-agnostic retrofit; no constrained decoding.
- [Outlines](https://github.com/dottxt-ai/outlines) — constrained decoding via finite-state machines over the model vocabulary: guarantees JSON-schema / regex / grammar conformance *during* generation (Apache-2.0); requires local or served model access.
- [BAML](https://github.com/BoundaryML/baml) — schema-as-contract DSL with Schema-Aligned Parsing (post-hoc, tolerant of markdown/CoT preambles), compiled to typed functions in several languages (Apache-2.0). Fits contract-first pipelines even when a model lacks native tool-calling. Its [`feelings`][baml-feelings] demo repo (no LICENSE file as of 2026-09-30 — [issue #1][baml-feelings-issue1] asks for one, still open — treat as all-rights-reserved) extends every type with `.feels()`, `.how()`, `.matches<T>()`, `.judge<T>()`, `.fill<T>()` and `.ask()`, backed by TypeSafe's Jev ([jev-analysis.md](../infrastructure/jev-analysis.md)); `.fill<T>()` sends one request per class, not per field ([BAML/Jev blog post][baml-jev-blog]).
- [Guidance](https://github.com/guidance-ai/guidance) — grammar-constrained generation interleaving prompt control flow with sampling (MIT); local/vLLM backends.
- [Pydantic AI](https://github.com/pydantic/pydantic-ai) / [Marvin](https://github.com/PrefectHQ/marvin) — agent frameworks that validate outputs against Pydantic models by construction, with auto-retry on mismatch (MIT / Apache-2.0).

### Guardrails / policy

- [Guardrails AI](https://github.com/guardrails-ai/guardrails) — composable pre/post validator pipeline (PII, toxicity, schema, relevance) with a Hub of pre-built validators and retry-on-violation (Apache-2.0).
- [NeMo Guardrails](https://github.com/NVIDIA-NeMo/Guardrails) — Colang DSL for dialog-flow rails (topicality, jailbreak, self-check input/output) that models full conversation state, not just single-turn I/O (NVIDIA).
- [LLM Guard](https://github.com/protectai/llm-guard) — provider-agnostic input/output scanners: PII anonymization, prompt-injection classifiers, toxicity, secrets detection (MIT).
- **Safety classifiers** — Llama Guard / ShieldGemma are fine-tuned hazard-taxonomy classifiers run as a pre/post filter (Llama / Gemma community licenses, use restrictions); Lakera Guard is the hosted closed-source equivalent.

### Decision models (typed yes/no, choice, score)

A third validator shape, distinct from schema conformance and safety filtering: a cheap
typed decision about the output (yes/no, a choice among options, or a rubric score) that
code branches on directly, backed by a probability rather than free text.

- [Jev (TypeSafe AI)](../infrastructure/jev-analysis.md) — hosted "System One" classifier
  returning a probability for a yes/no (`noul`), a distribution plus confidence for
  `choice`, or a rubric score for `score`; see the linked analysis for pricing, limits,
  and the qte77/feelings measured pre-CI code-review-gate pilot. It ranks changes well,
  but its threshold needs setting per codebase — a fixed 0.70 cutoff wrongly flagged
  23–30% of clean changes on a codebase it wasn't tuned on, vs. 1.7% on the ones it was.
- [Laya](https://github.com/NandhaKishorM/laya) ([full entry](../reference/system-1-decision-models-landscape.md#laya-nandhakishorm)) — open-weight (Apache-2.0)
  non-autoregressive alternative; its README claims its answer payload is
  schema-identical to Jev's (`choice`/`score`/`noul` plus a token-usage block), so an
  existing Jev client can repoint its base URL. Full entry:
  [#517](https://github.com/qte77/ai-agents-research/issues/517) (system-1 decision
  models and the Jev ecosystem).

### Verification / fact-checking

- [Bespoke-MiniCheck](https://huggingface.co/bespokelabs/Bespoke-MiniCheck-7B) — fast claim-vs-document grounding checker; a binary support score maps naturally onto confidence-tagging of extracted facts (**CC BY-NC 4.0 — non-commercial**; commercial license separate).
- [FActScore](https://github.com/shmsw25/FActScore) — decomposes long output into atomic claims and verifies each against a knowledge source (MIT); higher latency, gold-standard for biographical/encyclopedic factuality.
- **Self-consistency** (sample-N + semantic majority vote for output stability) and **property-based testing** (assert output *properties* — schema shape, field presence, value bounds — across prompt variations) are dependency-light techniques rather than tools.
- For CI eval gates, [DeepEval](https://github.com/confident-ai/deepeval) (under RAG evaluation above) doubles as a faithfulness/hallucination output-quality gate.

## Production Patterns & Reference Frameworks

- [12-Factor Agents][12fa-blog] ([GitHub mirror][12fa-gh]) — principles for production-grade LLM agents (Dex Horthy / HumanLayer, 2025-04-03). Full treatment: [mas-design-principles.md](../../sdlc-lcm/mas-design-principles.md).
- [Agents Towards Production](https://github.com/NirDiamant/agents-towards-production) — end-to-end playbooks for shipping agents.
- [Learn Harness Engineering (WalkingLabs)](https://github.com/walkinglabs/learn-harness-engineering) — project-based course on *harness engineering* for reliable AI coding agents: structuring Instructions, State, Verification, Scope, and Session Lifecycle around the model instead of fine-tuning it (12 lectures + 6 projects, framed around Claude Code / Codex; MIT). Maps onto [CC-agentic-harness-patterns-analysis.md](../../cc-native/agents-skills/CC-agentic-harness-patterns-analysis.md).
- [Hands-On Modern RL (WalkingLabs)](https://github.com/walkinglabs/hands-on-modern-rl) — practice-first RL curriculum from classic control to LLM post-training (RLHF, DPO, GRPO, RLVR, DeepSeek-R1) and agentic RL (multi-turn credit assignment, tool-use trajectories, Deep Research); Python/PyTorch (CC BY-NC-SA 4.0, non-commercial).
- [Compiling Agentic Workflows into LLM Weights](https://arxiv.org/abs/2605.22502) — Dennis et al. (2026-05-21) argue for *compiling* an agent's orchestration procedure into the weights of a small fine-tuned model instead of an external framework, reporting near-frontier quality at ~2 orders-of-magnitude lower cost — with no context-window or orchestration overhead — across travel-booking, support, and insurance-claims workflows (14–55 nodes). A weight-level counterpoint to the graph/framework orchestration in §1 (paper claims; methodology not independently verified).
- [Beyond Global Replanning: Hierarchical Recovery for Cross-Device Agent Systems](https://arxiv.org/abs/2606.20487) — Yao et al. (Shanghai Jiao Tong University et al., arXiv:2606.20487, 2026-06-18) propose **H-RePlan**, splitting multi-device agent failure recovery into device-local strategy recovery vs. orchestrator-level global replanning via a compact cross-layer failure abstraction, plus **HeraBench** (23 seed tasks → 174 fault-injected variants across a 4-device Linux+Android testbed) to evaluate the distinction. Reported vs. a UFO3-GUI baseline: 75.84% vs 46.86% completion, 36.78% vs 13.79% perfect-pass rate, and ~5.44× lower token cost per perfect pass (paper claims; methodology not independently verified; no code/benchmark repo published as of 2026-07-23).
- [TradingAgents (Tauric Research)](https://github.com/TauricResearch/TradingAgents) — open-source multi-agent framework modeling a trading firm on **LangGraph**: an analyst team (fundamentals / sentiment / news / technical), bull/bear researchers who debate, a trader agent, and a risk-management/portfolio-manager layer that approves or rejects trades; SEC EDGAR + Yahoo Finance data, backtesting, checkpoint resume. Multi-provider (OpenAI, Anthropic, Google, xAI, DeepSeek, Qwen, …); explicitly framed as **research-only, not financial advice** ([paper](https://arxiv.org/abs/2412.20138)) (Apache-2.0; 108k★, `gh api` 2026-09-24).
